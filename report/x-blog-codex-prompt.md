刚切过来的第一周，体验非常拧巴：它能干活，但实在太重了。你让它改一百多行业务逻辑，它转身往仓库里塞进七百行单元测试、一串防御性 `try/catch`、单次调用的 helper 函数，以及把代码再翻译一遍的注释。为了跑通那堆新写的测试，它还会在终端里一轮接一轮地编译和重试。Token 烧得飞快，等它停手的时间很长，最后审代码时还得在一大片测试文件里翻找真正的业务改动。

### 这份系统提示词到底改了什么

Codex 内置的系统提示词里有一句很软的话：“不要为低影响改动写测试，如果写测试要确保有意义”。对模型来说，这句话约等于“每次都写一套完整的测试文件交差”。如果只在 `AGENTS.md` 里追加规则，模型还要跟内置系统提示词左右互搏，所以我直接对系统提示词做了原生 Override（完整文件：`[贴你的提示词链接或 Gist]`）：

1. **除非用户开口要，否则不写新测试文件；改用“反向读源码 + 最小入口验证”**。写完代码后，先在内部反过来走查一遍：修 Bug 就从入口和输入顺推到输出；写新功能就从已实现的代码倒推需求，找漏掉的分支和站不住脚的假设。走查完还有拿不准的地方，只针对那个问题跑一次现成的测试，或者用临时脚本调一下真实入口。
2. **只在系统边界做防御**。网络、外部 API、第三方数据和用户输入才需要校验与重试；项目自己的内部代码直接让错误暴露出来，少写吞异常的 fallback，也不提前拆只用一次的 helper。
3. **注释只写代码表达不了的外部事实**。比如上游 bug、平台限制或协议标准。代码本身能看懂的逻辑，一行注释都不写。

### 扒完 240 条运行轨迹后，两个反直觉的发现

为什么砍掉 91% 的落盘测试，通过率反而更高了？我把 240 次运行的全部工具调用、测试输出和失分原因逐一拆了一遍，找到了原因。

![240 条轨迹深度复盘：测试有效率与单字符死角](file:///C:/Users/padyu/Documents/gpt-trial/deepswe-fresh60-coding-20261026/report/x-article-card-2-deepdive.png)

#### 1. 模型狂写的那几百行测试，真正抓到 Bug 的不到一半

在原版提示词的 120 次运行里，模型有 119 次新建或扩写了测试文件，平均每次往仓库里塞将近 700 行。但顺着执行日志看它到底靠测试抓到了多少问题：
- 只有 **48.3%（58/120）** 的运行里，它写的测试真正经历了“先红后绿”，也就是测试报错、逼着它回头修好了生产代码里的 Bug。
- 剩下的 **51.7%（62/120）** 里，大半是一遍全绿的陪跑；更要命的是**“同源假绿”**：当模型对需求理解偏了，它用同一个错误假设去写业务代码和测试断言。比如在 `happy-dom` 任务里，两组共 4 次运行全都漏掉了“脱离 DOM 树的几何计算”等 4 个场景（10/14 通过）。原版每次写了六七百行测试，在本地跑得全绿，但测试和实现错在了同一个地方。

相比之下，Override 版在 `query` 和 `valibot` 这种任务上完全不留测试文件（原版每次留 1,200 到 1,500 行测试），只靠反向源码走查加一个简短的临时脚本验证类型和入口，4 次运行照样全部满分通过，写出来的核心源码还短了 10% 左右。

#### 2. 未通过的题，几乎全是底层 Parser、编译器和代码格式化；去掉它们，常规业务通过率高达 84.6%

再去翻那些没通过的任务，会发现它们高度集中在 **手写 JS 词法解析器、SQL/Rego 语法格式化、AST 还原、ANSI 转义字节流截断** 这类重度编译/文本解析任务上。

而且模型在这些题上也不是不会写，**几乎全都跑通了 94%～99% 的官方测试，最后卡在 1 个字符潜规则上**：
- **`obsidian-linter`（Markdown 链接转换）**：4 次运行全部 **59/60** 通过。唯一挂掉的那 1 个，是遇到带空格的文件名时，模型按 CommonMark 标准输出了 `[My Page](<My Page>)`，而该仓库的测试偏偏要求不加尖括号的 `[My Page](My Page)`。
- **`meriyah`（手写 JS 语法解析器）**：跑通了全部 51,469 个存量测试和 **48/49** 个新测试。唯一漏掉的是 `for (using of of [1, 2])`（把上下文关键字 `of` 同时当变量名声明）。
- **`termenv`（ANSI 控制字节截断）**：**34/35** 通过。唯一挂在传入 `width = 0` 时，模型写了 `if width <= 0 { return "" }`，但官方测试要求 0 宽度下仍保留零宽度的超链接开启与闭合控制字节。
- **`sqlfmt`（SQL DDL 格式化）**：复杂的建表子句全写对了（**30/32** 通过），挂掉只因为输出了 `CREATE TABLE foo(`，而仓库第 200 号测试快照要求左括号前必须留一个空格：`CREATE TABLE foo (`。

说白了，并发、状态机、API、数据库和日常工程架构的逻辑漏洞，模型顺着源码走查就能推出来；但“左括号前留不留空格”、“链接加不加尖括号”属于仓库私有的字符潜规则，读十遍源码也推不出来。

更重要的是：**绝大多数人平时根本不会拿它手搓底层 Parser、编译器或代码格式化器。**
如果我们把这 8 道重度 Parser / 格式化 / AST 题从样本里拿掉，只看剩下的 **52 道常规工程与业务开发任务（104 次尝试）**：
- 原版系统提示词通过率是 **75.0%（78/104）**；
- Override 版直接拉到了 **84.6%（88/104，净胜 +9.6 个百分点，单任务 10 胜 1 负）**。

如果你真要用它写底层 Parser 或 Formatter，只需要在提问时自己加上一句约束：“先去读同目录下的存量测试快照确认空格与转义约定，再测一下零宽和关键字重名边界”，就能把这块死角补上。

### 怎么用上这份 Override 系统提示词

这份文件是完整的 **System Prompt Override**，不是追加在后面的个人指令，所以不会和内置提示词打架。

用法很简单：把这份 [`override-coding.md`](file:///C:/Users/padyu/Documents/gpt-trial/deepswe-fresh60-coding-20261026/prompts/override-coding.md) 丢给你的 Codex，直接让它用原生方式把默认系统提示词替换掉就行。换完之后，每次改动立省四分之一的 Token 和近五分之一的等待时间，拉出来的 diff 干净利落，一眼就能审完。
